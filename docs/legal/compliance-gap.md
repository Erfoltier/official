## 1. 法令上の位置づけの整理（案）

| 論点 | 整理の案 | 根拠 |
|---|---|---|
| 扱う情報の種類 | 施術歴・カルテ補助メモ・写真・同意書・問診票には病歴などが入るため、**要配慮個人情報**にあたると考えられます。取得には原則として本人の同意が必要です。ただし、医療機関が診療のために患者本人から直接受け取る場合は、同意があると考えられる場面が多いとされます | 個情法 第2条第3項・第20条第2項、医療ガイダンス |
| 院とエアフォルティアの関係 | 院が患者情報の持ち主（管理の責任者）で、エアフォルティアは院から**取扱いを任された側（委託先）**になる案です。委託であれば、院からエアフォルティアへ渡すことは「第三者提供」にあたらず、患者の同意は要りません | 個情法 第27条第5項第1号 |
| 委託でいられる条件 | エアフォルティアが患者情報を**自分の目的に使わない**こと（例：院をまたいだ分析、営業、AI の学習に使わない）。使うと委託の範囲を超え、第三者提供になるおそれがあります | 個情法 第27条第5項第1号、個人情報保護委員会 Q&A |
| 院の義務 | 委託先（エアフォルティア）を選び、監督する義務があります。そのため院は契約・安全管理の説明・監査への協力を求めてきます | 個情法 第25条、厚労省GL 経営管理編 |
| エアフォルティアの義務 | 提供事業者GLに沿った安全管理と、院への説明（サービス仕様適合開示書など）を行います | 提供事業者GL |
| 外国の会社の利用 | 外国の会社のサーバー（Google など）に患者情報を置く場合は、「外国にある第三者」への提供のルールと、委託先の安全管理の確認が関わります。**国内にデータを置く業者を選ぶ**のが説明しやすい形です | 個情法 第28条、厚労省GL、提供事業者GL |
| 漏えいしたとき | 要配慮個人情報は**1件でも**、漏えい（またはそのおそれ）があれば、院から個人情報保護委員会への報告と本人への通知が必要です。委託先は院にすぐ知らせる必要があります | 個情法 第26条、施行規則 第7条第1号 |
| 電気通信事業の届け出 | LINE などで院と患者のやりとりを**中継**する機能を持つ場合、電気通信事業の届け出が必要になるかを確かめる必要があります。予約を記録するだけなら不要と考えられますが、チャットの中継は判断が分かれます | 電気通信事業法 第2条・第16条（要確認：総務省「電気通信事業参入マニュアル」） |

## 2. いまの作りでできていること（確認できた範囲）

| できていること | 関係する要求 |
|---|---|
| 保存データを1件ずつ暗号化（AES-256-GCM） | 厚労省GL・提供事業者GL：保存時の暗号化 |

## 3. 足りない点と改修の提案

優先度：**A＝今すぐ（いしだ皮フ科の運用にも関係）／B＝他院に売る前に必ず／C＝売ったあと順次**

### A：今すぐ

| # | 足りない点 | なぜ問題か（根拠） | 提案 |
|---|---|---|---|
| A1 | README に「本番の認証と外部の脆弱性診断（セキュリティの弱点の検査）が済むまで、実際の患者情報を入れないこと」と書かれているが、本番では稼働している | 書かれた前提と実際の運用が食い違っています。何かあったときに説明がつきません（厚労省GL：リスク評価・運用管理規程） | ①今の安全対策で運用してよいかを院長が判断し、その判断を記録する。②外部の脆弱性診断を受ける日を決める。③README の書き方を実態に合わせる |
| A2 | **暗号鍵（config.php）とデータ（data/）が同じサーバーに置かれている** | サーバーが乗っ取られると、鍵とデータが一緒に盗まれ、暗号化の意味がほぼなくなります（提供事業者GL：暗号鍵の管理） | 販売用の環境では、鍵を別の場所（鍵の管理サービスなど）に置く。いしだ皮フ科の環境では、少なくとも鍵の控えをサーバーの外の安全な場所に保管し、保管した人と場所を記録する |
| A3 | 初期スタッフのPINが試作用で共通（README の記載） | 本番で変えていない場合、だれでも他人として入れます（厚労省GL：利用者の識別・認証） | 本番のPINが全員変わっているかを院長が確かめる。初回ログイン時にPINの変更を強制する仕組みを提案 |
| A4 | Basic 認証のID・パスワードを院のスタッフ全員で共有していると考えられる | 退職者が出ても入口の鍵が変わらないと、外から入れる状態が続きます | 退職・異動のときに入口のパスワードを変える手順を決める。将来は端末の登録に置き換える（A5） |
| A5 | 認証が「知っていること（PIN）」だけで、二要素認証（2つの方法で本人を確かめる）がない | 厚労省GL 第6.0版は、**2027年度の時点で動いているシステムを新しく入れたり更新したりするときは、二要素認証かそれに相当する対応を求めています** | README の予定どおり、パスキー（指紋・顔）と端末の登録を入れる。販売前には必須にする |
| A6 | バックアップが同じサーバー上にある（README：直近30個） | サーバーの故障やランサムウェア（データを人質に取るウイルス）で、本体とバックアップが同時に失われます（厚労省GL：バックアップは別の場所に、ネットワークから切り離した控えも） | 毎日、サーバーの外（別の業者・別の場所）へ暗号化したまま控えを送る。少なくとも1つは書き換えられない形で残す。**戻す練習**も年1回以上行う |

### B：他院に売る前に必ず

| # | 足りない点 | 根拠 | 提案 |
|---|---|---|---|
| B1 | 共用サーバー（ロリポップ）で動いている | 他の契約者と同じサーバーで、安全基準や置き場所の説明がしにくいです（提供事業者GL：クラウドの選び方・説明） | saas-plan.md のとおり、国内のクラウドへ移す。データを置く場所が日本国内であることを契約で約束できる業者を選ぶ |
| B2 | サービス仕様適合開示書がない | 提供事業者GL 第2.0版で、院への説明に使う書類として求められています。院が導入を判断するときに求めてきます | 提供事業者GL の様式に沿って作る（別の文書として作成を提案） |
| B3 | 院ごとにデータが確実に分かれていることの説明・確認がない | 院をまたいでデータが見えると、重大な漏えいになります | 院ごとに環境を分ける形（saas-plan.md の C）を保つ。将来1つのシステムにまとめるときは、院をまたいで見えないかの検査を必ず行う |
| B4 | 委託契約・利用規約・プライバシーポリシーがない | 個情法 第25条（院による委託先の監督）、提供事業者GL（契約での取り決め） | dpa-draft.md・terms-draft.md・privacy-draft.md で下書きする（⑤⑥） |
| B5 | 漏えい・障害が起きたときの手順書がない | 個情法 第26条（要配慮は1件でも報告）、提供事業者GL（事故のときの対応） | 「気づいてから○時間以内に院へ連絡」「院が委員会へ報告するのに必要な情報を出す」を手順書にし、年1回練習する |
| B6 | 退会したときのデータの返し方・消し方が決まっていない | 提供事業者GL（契約が終わったときの取り扱い）、厚労省GL | 院が読み取れる形（CSV・PDF・写真ファイル）で返し、決めた期間のあとに消し、**消したことを証明する書類**を出す。バックアップからも消える時期を明記する |
| B7 | 閲覧の記録・操作ログの保存期間が決まっていない（saas-plan.md 4-5） | 厚労省GL：アクセスの記録を一定期間残し、定期的に確認すること | 保存期間（例：5年）を決め、古いものは別の場所に移して残す。院長が定期的に確認できる画面を用意する |
| B8 | 脆弱性診断（セキュリティの弱点の検査）を外部に頼んでいない | 提供事業者GL（セキュリティの確認） | 販売前に1回、大きな変更のあとにも行う。結果の要約を院への説明資料に入れる |
| B9 | 運営側のスタッフ（エアフォルティア）が患者情報を見られるかどうかの決まりがない | 提供事業者GL（運営側の権限管理）、個情法 第24条（従業者の監督） | 「原則として見ない。障害対応で必要なときは院の許可を得て、記録を残す」と決め、仕組みでも制限する |
| B10 | 同意書・写真の取得について、患者への説明の文面がない | 個情法 第21条（利用目的の通知）、第20条第2項 | 院が患者に見せる説明文のひな形を privacy-draft.md に用意する |

## 4. 外部サービスとのつながり（概要。詳しくは⑦で追記）

| サービス | 個人情報の流れ | 気をつけること（要確認） |
