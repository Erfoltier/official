# レーンリザーブ 販売に向けた設計と見直し

作成：2026年10月。いしだ皮フ科で動いている予約カレンダーを「レーンリザーブ」として、株式会社エアフォルティアコンサルティングから他院・サロンへ販売するための方針です。

---

## 1. 全体の形（どこで動かすか）

### 結論
- **販売先にサーバーを契約してもらう形はとらない。** こちら（エアフォルティア）がまとめて運営する「クラウドサービス」として提供する。
- **最初は「院ごとに中身を分けて立ち上げる」形（下のC）で始め、契約が増えたら「1つのシステムを全院で共有する」形（B）へ移る。**

| 形 | 内容 | 判断 |
|---|---|---|
| A. 販売先がサーバーを契約 | 院ごとにサーバーを借りてもらい、そこへ入れる | ×：設定・更新・障害対応が院の数だけ発生。サロンはサーバーを扱えない。安全対策と責任があいまい |
| B. 1つのシステムを全院で共有 | Airリザーブ などと同じ一般的な形 | ◎（将来）：更新が1回で済む。ただし今の作り（1院専用）からの作り直しが大きい |
| C. 院ごとに分けて、こちらで運営 | 同じプログラムを院ごとに立ち上げ、データは院ごとに別 | ○（最初）：今の作りをほぼそのまま使える。データが院ごとに完全に分かれ、医療情報の点で説明しやすい |

### 写真の置き場所
- 今は写真・同意書PDFなどを、予約データと同じデータベースファイルの中に暗号化して入れている。
- 販売用は、写真を**オブジェクトストレージ**（写真などのファイル専用の保管庫。容量の上限が実質なく、使った分だけ払う）へ分ける。暗号化は今と同じく保存前にこちらで行う。
- 候補（国内にデータを置けるか、を最優先）
  - さくらのクラウド オブジェクトストレージ（国内・医療系の導入実績が多い）
  - AWS S3 東京リージョン（国内。データを外へ出すときの転送料がかかる）
  - Cloudflare R2（転送料がかからず安いが、保存先を日本に指定できない。サロン向けの将来候補）

### サーバー（プログラムとデータベース）
- 今のロリポップ（共用サーバー）は、いしだ皮フ科1院で使う分には十分。販売用には向かない（他の契約者と同居・容量・安全基準の説明のしやすさ）。
- 販売用は国内のクラウド（さくらのクラウド、AWS 東京など）に移す。データベースは、院が増えたら SQLite から MySQL か PostgreSQL へ。

### 費用の目安（概算・税抜。契約前に各社の最新料金で確かめる）
| 項目 | 目安 |
|---|---|
| 写真の容量 | ネオボ撮影1回 約12枚×約1MB、1日20回撮影する院で 月 約7GB、年 約90GB |
| オブジェクトストレージ | 1GB あたり月 数円 → 1院あたり年 数百〜千数百円（写真が多い院でも） |
| サーバー（10〜30院まで） | 月 数千〜1万円台 |
| バックアップ（別の場所に毎日） | 月 数百〜数千円 |

→ 月額料金に「写真 ○GB まで込み、超えた分は ○円/10GB」と入れておけば、写真が多い院でも赤字にならない。

### 医療機関に売るときに必要なもの
- 経済産業省・総務省の「医療情報を取り扱う情報システム・サービスの提供事業者における安全管理ガイドライン」に沿った説明資料（サービス仕様適合開示書）。クリニックは導入前にこれを求めることが多い。
- 利用規約・プライバシーポリシー・データ処理（委託）の取り決め、退会時のデータの返し方と消し方。
- データの保管場所が国内であること、暗号化、バックアップ、障害時の連絡体制の説明。

## 2. クリニック用とサロン用で機能を分けるか

### 結論：**プログラムは1つのまま、「業種」を選ぶと言葉と初期設定と出す機能が切り替わる形にする。** 別々の製品にはしない。

分けて作ると、直すたびに2か所を直すことになり、運営の手間が倍になる。中身は共通にして、見せ方だけ変える。

| | クリニック（美容皮膚科・美容外科） | エステ・脱毛サロン | 美容室・ネイル・まつげ |
|---|---|---|---|
| 呼び方 | 患者・カルテ・診察券番号 | お客様・施術記録・会員番号 | お客様・カルテ・会員番号 |
| レーンの初期例 | 医師・看護師・レーザー室・ネオボ | 個室1〜3・担当者 | スタイリスト・席 |
| 状態の初期例 | 来院済・医師待ち・処置中・会計待ち | 来店・カウンセリング・施術中・会計 | 来店・施術中・会計 |
| 出す機能 | 同意書・カルテ（既往歴・内服）・問診票・電子カルテ照合・ネオボ連携・写真比較 | 同意書（任意）・問診票・写真比較・回数券（今後） | 写真（仕上がり）・来店周期のお知らせ（今後） |
| 隠す機能 | — | 医療用の項目（既往歴・内服は「体質・注意事項」に言い換え） | 同意書・既往歴・ネオボ |

- 実装は「院の情報」に `業種` を1つ足し、言葉の表・初期設定の表・機能のオンオフで切り替える。今の配色プリセットと同じ考え方で作れる。
- サロン向けには「回数券・コース消化」「次回来店のお知らせ」があると売りやすい（今はない。販売後の追加候補）。

## 3. 無料版を作るか

### 結論：**ずっと無料の版は作らない。「30日間の無料お試し」と、安い「ライト」プランで代える。**

理由
- 写真は保管するだけで費用がかかり続ける。無料の院が写真をため続けると赤字になる。
- 医療情報・顧客情報を預かる以上、無料でも安全対策と問い合わせ対応の責任は同じ。
- 無料版は「使わないまま放置された院」のデータが増え、管理の手間だけが増えやすい。

代わりの案
| プラン | 内容の例 | ねらい |
|---|---|---|
| 30日間無料お試し | 全機能。終わったら有料にするか、データを書き出して終了 | 試してから決めたい院の不安をなくす |
| ライト | レーン2本まで・写真 5GB まで・スタッフ3人まで | 小さなサロン・個人店向けの入口 |
| スタンダード | レーン無制限・写真 50GB 込み | 標準 |
| クリニック | スタンダード＋同意書・カルテ・電子カルテ照合・ネオボ連携・安全管理の資料 | 医療機関向け |

- 料金の水準は、競合（Airリザーブ、RESERVA、Choice RESERVE、サロンボード など）の公開価格を調べてから決める。

## 4. 今の作りの無駄・見直し（点検結果）

重要な順。★は販売前に必ず直すもの。

### ★ 4-1. 写真がデータベースの中にあり、バックアップのたびに丸ごと複製される
- 写真・PDF（`blobs` 表）と縮小版（`thumb:` で始まるもの）が、予約データと同じデータベースファイルに入っている。
- 「保存データの控え（バックアップ）」は写真ごと丸ごと複製し、**最新10個まで残す**。写真が10GBなら、控えだけで最大100GBを使う。
- 控えを作るのに時間がかかり、共用サーバーの時間切れの原因になりうる（M3照合の反映では、写真を除いた軽い控えに切り替えて対応済み）。
- 対応：写真を専用の置き場（まずはサーバー上の暗号化ファイル、販売用ではオブジェクトストレージ）へ移す。データベースの控えは軽くなり、写真は「増えた分だけ」別に控える。
  - ※ 本番のデータを移す作業になるため、実施前に院長の承認をもらってから行う。

### ★ 4-2. 患者を探すたびに、全患者を読み込んで暗号を解いている
- 名前での照合・重複チェック・検索などで、毎回すべての患者を読み込んでいる（今は数千〜1万人規模で問題ないが、患者が数万人の院では遅くなる）。
- 対応：検索用の索引（暗号化した値から作る、名前のよみ・電話・番号の照合用の鍵）を持ち、全件を読まずに探せるようにする。販売前に。

### ★ 4-3. Node.js 版と PHP 版の2つを同じ機能で持っている
- ロリポップで動かすために PHP 版を作り、開発用に Node.js 版も残しているため、機能を足すたびに2か所を直している（照合・保存の中心部分だけで両方合わせて約8,000行）。最近は PHP 版だけに入れた機能もある（統合の取り消しなど）。
- 対応：販売用のクラウドへ移るときに、どちらか1つ（クラウドなら Node.js 版）にまとめる。それまでは PHP 版を正とする。

### 4-4. 消したファイルの中身が残り続ける
- 写真やPDFを「削除」すると、一覧から消えるだけで、中身は保存されたまま（取り消しのため）。縮小版も残る。
- 対応：削除から一定期間（例：90日）たったものを本当に消す処理を足す。サンプル患者の一括削除でも縮小版が残るので一緒に直す。

### 4-5. 閲覧の記録（だれがどの患者を見たか）が無期限にたまる
- 1人のスタッフが1人の患者を1時間に1件の記録。年に数万〜十数万件。
- 医療情報の安全管理では一定期間の保存が求められるため、消すのではなく「○年より古いものは別ファイルへ書き出して本体から外す」形にする。

### 4-6. 院ごとに違う設定がプログラムの中に書かれている
- いしだ皮フ科のメニュー・レーン・料金表の初期値、ゼオの料金表、ホームページの料金表の読み取り先などが、プログラムの中に入っている。
- 対応：販売用では「院ごとの初期設定ファイル」へ外に出し、業種別のひな形（第2章）と入れ替えられるようにする。

### 4-7. その他、細かい点
- 予約・記録・ファイルの「誰が作った・直した」の記録の形が、種類によって少しずつ違う。そろえておくと、操作ログや統合の取り消しが単純になる。
- 写真の縮小版は、写真を受け取ったときに作っておくと、写真比較を初めて開くときが速くなる（今は初めて見たときに作る）。
- 業種・院名・ロゴ・ドメインを、院ごとの設定から読む形にしておく（レーンリザーブとしての見た目）。

---

## 5. 進める順番（案）

1. **写真の置き場所を分ける**（4-1）。いしだ皮フ科でも控えが軽くなり、すぐ効果がある。※本番データを移すので、実施前に承認をもらう。
2. **消したファイルの整理・閲覧記録の書き出し**（4-4・4-5）。
3. **業種の切り替え**（第2章）と、院ごとの初期設定を外に出す（4-6）。
4. **販売用クラウドを決めて、院ごとに立ち上げる仕組み**（第1章のC）。あわせて 4-2・4-3。
5. 利用規約・プライバシーポリシー・安全管理の説明資料、紹介ページ（lanereserve.jp）。

## 6. 予約の入口の統合（LINE・Instagram・X・ホームページ・ホットペッパー）

### 方針
- 入口が増えても、スタッフが見る場所は1か所にする。
- **形の整った予約（予約フォームから来たもの）は自動で予約カレンダーへ入れる。**
- **自由な文章で届いた依頼（DM など）は「予約リクエスト受付箱」に集め、AI が希望日時・メニュー・名前の下書きを作り、スタッフが「この枠で確定」を押して入れる。** 確定すると相手へ確定のメッセージを返す。
- DM には自動返信で予約ページのリンクを返し、できるだけフォームへ誘導する。

### 入口ごとの対応
| 入口 | 対応 | 方法・注意 |
|---|---|---|
| LINE | ◎ 標準機能 | LINE公式アカウントの Messaging API で受け取る。LINE内の予約フォーム（LIFF）なら整った形で届く。今の「LINE申請の貼り付け」「連携API」を発展させる。院ごとに接続設定が要る |
| ホームページ・Googleマップ | ◎ 標準機能 | こちらの予約ページから直接入る。Google の予約ボタン連携は将来の候補 |
| Instagram の DM | ○ オプション | Meta の公式の仕組み（プロアカウント・アプリ審査が必要）で受け取り、受付箱へ |
| ホットペッパービューティー | △ オプション（サロン向けに重要） | 公開された仕組みがないため、予約のお知らせメールを読み取って取り込む。形式が変わると止まるので見張りが要る |
| X の DM | × 見送り | 公式の仕組みで DM を受け取るには高額な有料プランが要る。プロフィールに予約ページのリンクを置く |

### 作る順番（案）
1. 予約リクエスト受付箱（入口を問わず1か所に集める・AIの下書き・1回押して確定）
2. LINE（フォーム型）の自動取り込みと、確定メッセージの返信
3. ホームページの予約ページ
4. Instagram の DM、ホットペッパーのメール取り込み（オプション）
