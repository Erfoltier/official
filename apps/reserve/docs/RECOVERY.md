## 院内でまずすること（スタッフ）

| 状況 | すること |
|---|---|
| 予約表の上に黄色の帯「サーバーにつながりません」が出た | そのまま**見るだけ**で使う（今日〜7日先。変更はできない）。新しい予約・変更・キャンセルは**紙**に書く |
| 帯も出ず開けない（端末にダウンロードしていない、停電など） | 水曜・祝日なら、朝メールで届いた **予約表 PDF**（パスワード付き）を印刷して使う |

院のネットだけが止まったとき（スマホの電波では開ける）は、スマホのテザリングでパソコンをつなげば、いつも通り使える。

- 見張り：Lambda `lane-reserve-watch`（東京、1分ごとに https://monshin.ishidahihuka.jp/ を開く）→ CloudWatch アラーム `lane-reserve-down` → SNS `lane-reserve-down`

## 立て直す（Claude が行う。院長は「立て直して」と言うだけ）

1. **原因を見る**（5分）：AWS のサーバーの状態（EC2 の状態確認・AWS Health）。再起動で戻るならそれで終わり
2. **東京で立て直す**：`python3 ops/restore.py real`
   - いちばん新しい毎日の控え（午前3時）から新しいサーバーを立て、固定のアドレス（Elastic IP）を移す。**アドレス（reserve.・monshin.）は変わらない**
   - 2026-11-02 の練習：控えから立つまで **92秒**、起動して中身を確かめられるまで **約3分**
3. **東京ごと止まったとき**：`python3 ops/restore.py real --region ap-northeast-3`（大阪の写しから。DNS の向き先を自動で変える。切り替わりに5分ほど）。※大阪からの復元はまだ練習していない
4. **立てたあと**
   - 控えの時点の版で立つので、`release` で**最新の版を反映し直す**（練習では控えの版が 11/1 の壊れた版だった）
   - 予約データは**前日午前3時の時点**に戻る。それ以降に入った予約・変更は、院の端末の控え（帯の出る画面）・LINE・紙の記録から入れ直す
   - 院の Chrome の「LINE チャット連携」・自動予約・問診票はアドレスが同じなので、そのまま使える
   - 古いサーバーは、調べ終わるまで止めておく（消さない）
5. 記録：HISTORY.md に、止まった時刻・原因・戻った時刻・入れ直した件数を書く

## 練習（年に1〜2回）

本番の写しなので、そのまま立てるとリマインドや LINE を患者に二重に送ってしまう。**外へ通信できない状態**で立てる。

1. 本番と同じ VPC に、外向きの通信を全部消した入口（セキュリティグループ）と、SSM 用の通り道（VPC エンドポイント ssm・ssmmessages・ec2messages、本番からの SSM も通す）を作る
2. 毎日の控えから、その入口・公開アドレスなしで立てる（`NetworkInterfaces` で指定。`SecurityGroupIds`・`SubnetId` は一緒に渡さない）
3. SSM で：リマインドなどの自動実行を止める → 外へつながらないことを確かめる → 画面・問診票が中で開くか、患者・予約・問診票の件数
4. 片付け：サーバーを消す → 通り道を消す → 入口の規則を外してから入口を消す

2026-11-02 の結果：立つまで92秒、外へは出られない（LINE に届かない）ことを確認、問診票のページ 200、患者 4,053・予約 9,563・問診票 3,427 件が戻った。練習の資源はすべて片付け、本番の SSM が通ることも確かめた。
